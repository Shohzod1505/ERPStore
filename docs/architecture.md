# Архитектура

Статус: черновик. Документ уточняется по мере реализации.

## Почему так

Задача — offline-first MVP на один рабочий день. Приоритеты: корректные остатки и деньги, прозрачная история операций, минимум инфраструктуры. Поэтому выбран один модуль `:app`, Room как единственный источник истины и простая слоистая архитектура без микромодулей и `build-logic`.

## Слои

```text
ui -> domain -> data
```

- `ui` — Compose-экраны, ViewModel, неизменяемый `UiState`. Не знает про Room.
- `domain` — модели, интерфейсы репозиториев, use cases, бизнес-правила.
- `data` — Room-сущности, DAO, реализации репозиториев, мапперы.
- `di` — Hilt-модули.

ViewModel собирает состояние из use cases и отдаёт `StateFlow<UiState>`. DAO возвращают `Flow`, поэтому изменения в базе автоматически обновляют экран.

## Модель данных

| Таблица | Назначение |
|---|---|
| `products` | Товар: название, `unitsPerBlock`, средняя себестоимость в копейках. |
| `locations` | Склад или подсклад: `parentId = null` для склада. Один уровень вложенности. |
| `documents` | Закупка, продажа или инвентаризация: тип, статус, номер, дата, место, сумма. |
| `document_lines` | Строка документа: товар, количество, цена, снимок себестоимости. |
| `stock_movements` | Журнал движений: товар, место, ±штуки, себестоимость, документ, тип. |
| `cash_transactions` | Касса: тип, сумма, дата, комментарий, ссылка на документ. |

Остаток товара и остаток кассы не хранятся отдельными полями — они считаются суммой движений. Это даёт аудит и не позволяет «молча» перезаписать баланс.

Блоки не хранятся: `blocks = units / unitsPerBlock`. В UI показываются целые блоки и остаток в штуках. Деньги хранятся как `Long` в копейках, даты — как `Long` epoch millis; `java.time` не используется, чтобы не включать desugaring.

При создании черновика закупки или продажи сумма документа и сумма строки закупки рассчитываются сразу. У черновика продажи COGS остаётся нулевым до проведения; у инвентаризации сумма и корректировки появляются только при проведении.

## Проведение документов

Все изменения выполняются в одной транзакции Room. Перед проведением проверяется, что документ в статусе `DRAFT`.

### Закупка

1. Для каждой строки создать движение `+quantity` в месте документа.
2. Пересчитать среднюю себестоимость товара:
   `newAvg = (oldQty * oldAvg + qty * price) / (oldQty + qty)`.
   Если старого остатка нет, `newAvg = price`.
3. Создать расход кассы на сумму документа.
4. Перевести документ в `POSTED`.

### Продажа

1. Проверить остаток в месте документа по каждой строке. Если не хватает — вернуть ошибку, ничего не менять.
2. Зафиксировать COGS в строке: `quantity * product.averageCost`.
3. Создать движение `-quantity`.
4. Создать приход кассы на сумму документа.
5. Перевести документ в `POSTED`.

### Инвентаризация

1. Для каждой строки сравнить системный остаток в месте с фактическим. Экран заранее показывает все товары выбранного места.
2. Создать корректирующее движение на дельту.
3. Недостача оценивается по средней себестоимости и попадает в расходы P&L; излишек — в прочие доходы.
4. Перевести документ в `POSTED`.

## Касса и P&L

Кассовые типы: `INCOME`, `EXPENSE`, `DEBT_GIVEN`, `DEBT_RECEIVED`. Операции, созданные документами, имеют ссылку на документ; ручные операции ссылки не имеют.

P&L:

- выручка — проведённые продажи;
- COGS — снимки себестоимости в строках продаж;
- прочие доходы — ручные приходы и излишки инвентаризации;
- расходы — ручные расходы и недостачи;
- займы в прибыль не входят.

Ручной приход считается прочим доходом, ручной расход — операционным расходом. Касса одна, валюта — рубль.

Денежный поток считается отдельно: все приходы минус все расходы, включая займы. Так владелец видит и прибыль, и движение денег, не смешивая их.

## Компромиссы

- Один модуль и слоистая архитектура вместо микромодулей — быстрее и надёжнее для MVP.
- Один уровень складов и одно место хранения на документ — достаточно для ТЗ.
- Черновик можно только удалить; проведённый документ неизменяем, отмена проведённых и переводы между складами вне MVP.
- Средняя себестоимость общая по товару, а не по складу — проще и предсказуемее для небольшого магазина.
- Нет фильтров по датам и экспорта — отчёты показывают данные за всё время.

## Риски

- Hilt обязателен. Совместимость KSP и Hilt с AGP 9 и built-in Kotlin проверяется до написания фич; при проблемах ищем поддерживаемый в AGP 9 путь, а не заменяем Hilt ручным DI.
- Демо-данные должны создаваться через use cases, иначе остатки и COGS разойдутся с бизнес-логикой.
